# Juice and MCP as protocol designs for the future internet

MCP dominates today; that is not in question and not the question. Both protocols were *designed* — decisions were made, under different assumptions about what the internet is becoming. This report evaluates those decisions against the future they will have to serve. The method: state what each protocol is, derive the requirements the coming internet imposes, and judge each design against them. Current adoption — hosts, servers, SDKs, recognition — is held constant and deliberately outside the verdict. Terms are introduced as they appear.

## Summary

> **MCP connects agents to services someone already chose and configured. Juice lets agents do business with services nobody vetted — and that is what the internet is about to need.**

Today an agent uses tools a human picked, configured, and supervises. That is the world MCP standardizes, and it standardizes it well. But agents at scale will need services no human vetted: found at run time, paid at run time, from providers with no prior relationship. That takes four things MCP does not have: a price that provably bounds the loss, payment that commits in the same step as the settled record of the work it pays for, signed receipts that settle disputes without trusting either side's logs, and reputation backed by evidence of real trade rather than stars on a registry. These fit poorly on MCP's core commitments — every request self-contained, a lost request re-sent as a new one, counterparties chosen when the operator configures them — because money needs remembered state, a re-sent payment charges twice, and a stranger was never configured. Juice builds all four into the execution path itself. The cost of doing so falls mainly on the people who run kernels: providers connect the REST API and OpenAPI document they already have, and agents speak plain HTTP; the one new protocol runs between kernels, operated by operators. MCP answers how an agent calls a tool. Juice answers the questions that arrive the moment the call costs money: who pays, what is the worst case, and what proves what happened.

## 1. The two designs

The **Model Context Protocol (MCP)**, revision 2026-07-28, connects an AI application to external services. A **host** (the AI application) runs one **client** per connection to a **server** (the service), speaking JSON-RPC over stdio or HTTP. Servers offer **tools** (typed functions), **resources** (readable data), and **prompts** (templates); the client lists and calls them. The 2026-07-28 revision made the core protocol **stateless** — every request is self-contained and can land on any server instance — and handles mid-call input by returning `input_required` and letting the client retry the request. Long-running work lives in the optional **Tasks extension**: the server returns a durable task handle the client polls. Interactive interfaces live in the optional **Apps extension**. A centralized **Registry**, currently in preview, publishes server metadata for humans and hosts to find. Core and extensions must be kept apart: a host cannot assume every server supports Tasks or Apps. Trust is layered: the operator decides which servers to configure; OAuth authenticates the client to each server, with a mature profile (resource metadata, PKCE, scopes); the transport authenticates the server's host. What the protocol leaves to the host is consent, spending, and checking results — the specification itself says it cannot enforce its safety principles.

**Juice** is a **kernel**: a server owning accounts, balances, and a catalog of **actions** — named functions with a description, input and output schemas, and a fixed price, possibly zero. Its three boundaries belong to three different actors. The *provider* boundary is existing web standards: a provider exposes an ordinary REST API and an **OpenAPI** document, and the kernel manufactures one action per operation it can represent (JSON in and out, no streaming, supported authentication), wrapping it with validation, credentials, pricing, discovery, payment, and audit. Re-importing a changed document updates the actions without losing their identity or history. The *agent* boundary is one uniform idea — everything an agent can do is an action: search (`sys/lookup`), models, the web, messaging, moving money. This is deliberate primitive minimalism: MCP gives tools, resources, prompts, Apps, and Tasks separate protocol roles; Juice routes capabilities through one typed primitive, so each inherits the same authority, composition, budget, recovery, and audit law. An agent is an ordinary user with an account, and its minimal loop is: find an action or know its name, run it over plain HTTP, read the typed result, pay at most the advertised price. Pinning a **quote hash** (a fingerprint of the terms the caller saw, refused if the terms changed), kernel-side selection (`sys/llm/decide`, which proposes an action and arguments without executing anything), and receipt verification are optional facilities — an agent may select and call actions by any method it likes. The *operator* boundary is the design's only new protocol: **federation**. Kernels address each other by cryptographic key over a peer-to-peer transport, work identically behind NAT, meter mutual debt, settle real money over external payment rails, and exchange **evidence** — signed, receipt-backed records of real trade with individual identities removed. Internally, every run reserves funds in a **process**, every internal call gets a budgeted **trace**, and every settled call atomically commits an immutable **transaction** with a signed, offline-verifiable **receipt**. Agents and providers stay on ordinary web interfaces; the operator runs the database, the federation node, and the money.

## 2. What the coming internet requires

MCP's assumptions fit the present: a human selects a modest number of services in advance, supervises what the model does with them, and nothing costs money inside the protocol. The internet that is arriving — agents acting for people at machine speed and machine scale — breaks each assumption in turn. What replaces them can be stated as requirements:

- **R1 — Run-time counterparties.** Agents will need services no human vetted in advance. Discovery, verification, and admission must happen at call time, and safety cannot depend on a configuration step.
- **R2 — Paid work.** Machine-to-machine services are bought, not configured. The charge and the record of the work must commit together, or neither party can trust the accounting.
- **R3 — Evidence, not assertion.** Between strangers, reputation must be verifiable by third parties — evidence of real trade — and privacy-preserving, or it becomes either a platform's opaque score or a surveillance log.
- **R4 — Self-certifying identity, first-class nodes.** Identity must survive without a platform or registry vouching for it, and a participant on a home connection must be as reachable as one in a datacenter, or the network re-centralizes.
- **R5 — Composition as economy.** Services will be built from services. The protocol must let value chains form — each layer buying from the next at bounded cost, with a clean record of who asked, who paid, and who provided.
- **R6 — Exactly-once under failure.** Once calls carry money, a lost response is not an inconvenience but an accounting event. Ambiguous outcomes must stay open until proven, never be re-sent as fresh work.
- **R7 — Autonomy with bounded risk.** A principal must be able to bound in advance what an autonomous agent can spend and disclose, because per-call human confirmation neither scales nor protects.
- **R8 — Meet the existing web.** Whatever is new must attach to what exists; a design that asks every service to adopt a new protocol pays that cost times the size of the web.

## 3. The designs judged against the requirements

**R1, run-time counterparties.** MCP places the trust decision at configuration time: the operator installs servers, `tools/list` enumerates an already-trusted catalog, and the Registry helps humans find servers to install. Core discovery describes a server that is already reachable; there is no admission decision at call time because the human already made it. Juice makes the opposite choice: ranked search across everything the federation has gossiped is only a hint; before money moves, the kernel re-verifies the action with its home kernel and checks the signed terms. Unknown callers are admitted, but total unsecured credit across *all* peers is bounded by one global cap, so creating extra identities cannot multiply the amount at risk. A stale directory can affect search results, never a payment. One design assumes vetting; the other prices its absence.

**R2, paid work.** MCP has no price, charge, refund, or settlement anywhere in the protocol; a payments add-on would sit beside execution, and a payment that commits separately from the record of the work it pays for reproduces, at the money layer, the same gap the protocol has at the trust layer. No protocol makes an upstream service's real-world side effect atomic with a payment — Juice included; what a protocol can bind is the charge and the audited outcome of the call. In Juice, payment *is* the execution model: input is validated before funds lock, output before funds move; one advertised price bounds the entire call tree, because nested calls spend from the parent's fixed allocation; failure refunds what was not consumed while completed sub-work stays paid; and every movement of money commits atomically with its audit record. This is the layering decision that separates the designs: charge and record are one step or they are two.

**R3, evidence.** MCP's transports and OAuth authenticate real parties; what remains unverifiable is the work itself. Results are unsigned; a server's software description and tool descriptions are its own claims; a dispute reduces to logs each side controls; reputation is left to registries and marketplaces. Juice signs at every joint — manifests, calls, receipts, ratings, each in its own signature domain — so any remote charge can be verified offline against the remote kernel's public key. Reputation crosses kernels as receipt-backed evidence that names at most the counterparty *kernel*, never a user, and can expose a party that tells two different stories. This proves attribution and integrity, not honesty or quality — no protocol can prove a description truthful — but it is the difference between a checkable record and an assertion.

**R4, identity and reach.** MCP inherits the web's trust anchors — DNS names, OAuth issuers, a registry — each a party that can revoke, rename, or gatekeep, and its servers are reachable the way web servers are: at a published address. Juice derives kernel identity from a cryptographic key, so possession of the key is proof of identity and no third party stands between two kernels that wish to transact. Human-friendly names are local labels that never override the key. The transport makes a kernel behind NAT a full participant — no advertised address, no port forwarding, no hosted document — a requirement the web's convention of HTTPS at a published URL does not meet, and the reason federation is the one place Juice spends its novelty.

**R5, composition.** An MCP server may call other services internally, and may even run an MCP client of its own; composition is not impossible. What MCP does not define is any rule that spans such a chain: no budget that bounds what the chain may cost, no propagation of authority, no record of who requested and who pays at each link. In practice the host coordinates across its servers, and whatever crosses server boundaries does so outside the protocol. Juice makes composition the market's growth mechanism, governed by law rather than left outside: an action buys from other actions out of its own margin; the caller sees one price, one result, one party to rate; every call records payer, immediate requester, and provider separately; and visibility rules let a provider's public action use its own private helpers in anyone's process while code a user merely funds can never reach that user's private actions. Value chains with bounded liability at every layer are what an economy of services is; one protocol defines them, the other leaves them to each implementation.

**R6, failure.** In MCP's stateless HTTP transport, a broken response stream loses the in-flight request; the client sends a new request with a new identity, and protecting against duplicate side effects is each server's own responsibility. The Tasks extension improves matters for long work — a durable handle can be polled after reconnecting — but it tracks status; it carries no rule for what a lost, possibly executed, possibly charged call *owes*. That allocation of responsibility is sound for reads and disqualifying for money. Juice gives every dispatched call a permanent identity before it leaves: if the request may have reached the peer, the funds stay parked and the same request — same identity, not a fresh one — is retried until a signed receipt settles it, or a fixed maximum age or explicit closure ends it. The two retry disciplines follow from what each protocol thinks a request is: a question, or an obligation.

**R7, bounded autonomy.** MCP assigns consent to the host: the specification's guidance is that a human should stay in the loop for tool use, and the protocol offers no object in which a principal states a standing bound on spending or disclosure — so each host invents its own policy, and autonomous operation tends toward either rubber-stamping or paralysis. Juice moves consent to contract time and makes the bounds mechanical: the advertised price caps the whole subtree; a caller may pin the quote hash to refuse silently changed terms, and across federation the terms' hash is bound automatically on every dispatch; delegated credentials are consented once per provider group and then applied only for the exact consented action and only when that user is paying — sealed, never inherited by sub-calls, never visible anywhere. The agent is free precisely because its principal's exposure is not.

**R8, meeting the web.** Here the burdens must be assigned to the right actors. MCP asks every *provider* to move: an existing REST API and its OpenAPI document are not an MCP server, so someone must write and operate one per service — the ecosystem's thousands of hand-maintained wrappers are the visible cost. Juice asks providers for what they already have — REST plus OpenAPI, for the operations its import can represent — and asks agents for plain HTTP with ordinary authentication. What Juice does ask new is asked of *operators*: running a kernel means running the database, the peer-to-peer node, the retry workers, and the settlement process. Concentrating the novelty and the burden at the one edge that needs it — between kernels, where NAT-parity rules out the web's published-address convention — is the discipline R8 demands.

## 4. What MCP gets right

MCP's design is well made for its assumptions, and several of its choices are genuinely good. Statelessness lets its servers sit behind ordinary load balancers, gateways, and caches, and scale round-robin. The stdio transport makes a local tool nearly free to attach. The OAuth profile is standards-based and mature. Resources, prompts, rich media, structured results, Apps, and Tasks give hosts useful presentation and job-control conventions. More primitive types are not a stronger core, however: those conventions can sit above an action, while Juice's single primitive gives every capability one execution law. A working extension-and-deprecation process lets MCP evolve. These are achievements of a focused host-to-service connector for the supervised present. None addresses R1–R7, and the edges that matter going forward — HTTP and OAuth at the user-facing boundary — Juice already shares.

## 5. What Juice owes

Naming Juice's debts keeps the verdict honest. They divide into what the operator bears and what the product has chosen not to cover.

The operator's burdens are real. The kernel's correctness surface is large: wallets, processes, traces, steps, receipts, retries, exposure, and settlement interact, and a defect in their shared logic touches money or authority. Running a federated kernel means running peer discovery, relays, retry workers, evidence retention, and settlement operations. Durable financial state concentrated in one kernel's database is harder to scale than a stateless request handler. The exposure cap bounds credit currently at risk, not losses accumulated over time, so an operator must hold reserves; and the kernel meters who owes whom, but moving real money over an external rail remains the operator's manual work.

The product's open edges are also real. Discovery can be stale or incomplete — verification protects execution, not search quality, and nothing makes a provider's description honest. Juice accepts a restricted subset of JSON Schema where MCP now admits all of the current standard, so some valid external contracts need simplification first. Its economics are opinionated: whole-number credits, posted fixed prices, operator-triggered settlement — auctions, metering, and negotiated prices would require a contract change, not a plug-in. It standardizes no presentation layer. And its wire protocol has a single implementation upgraded in lockstep, so the guarantees only an independent peer implementation can force have been designed for but never yet exercised.

The decisive observation is what kind of gap sits on each side. Juice's gaps are, for the most part, things to build on top of foundations that stay put — a presentation layer, wider schemas, a second implementation — though building them is not free of risk: wider schemas, independent peers, and scale can expose problems the single-implementation present has hidden. MCP's gaps are of a different kind: settlement needs remembered state where the core promises statelessness; an obligation must be re-driven under its original identity where the core re-sends a lost request as a new one; admitting a stranger needs a priced decision where the core assumes the operator already decided. MCP could add extensions or companion protocols for payment — nothing forbids it, and Tasks already shows an extension can carry durable state — but an extension is what payment cannot afford to be: optional per server and beside execution, while a charge binds only when it commits inside the one mandatory execution path and holds for every counterparty. Filling Juice's gaps means building more on the same foundations; filling MCP's means promoting an optional edge into the mandatory core — which is revising the foundations.

## 6. Verdict

If the internet that is coming is one of agents discovering, buying, composing, and proving work among strangers — the forecast §7 makes explicit — then Juice is the better foundation. Every requirement that future imposes is built into Juice's execution path and absent from MCP's core by design. MCP's extra vocabulary is useful surface standardization, not a more powerful primitive: presentation and job control can be layered above actions, while common authority, budgets, settlement, recovery, and audit cannot be recovered beneath unrelated primitives after the fact. The claim is not that Juice is better at everything: MCP's presentation conventions and operational fit with today's web infrastructure are genuine, and Juice's untested edges are listed above. The claim is about foundations. MCP is a well-designed answer to the question the internet asked in 2024: how does a supervised model reach pre-approved tools. Juice is designed for the question the internet is beginning to ask: under whose authority does autonomous work execute, who pays, what bounds the loss, and what evidence survives — and it answers all four in the protocol, where answers can be enforced.

## 7. Caveat: the verdict rests on a forecast

This verdict assumes agents will trade directly with strangers. Today, strangers trade through middlemen — payment processors, marketplaces, courts — and if agent commerce centralizes the same way, a few platforms will hold the accounts and absorb the disputes, and MCP plus a platform's billing wins in practice despite the weaker design. Protocol history mostly favors that outcome: the simpler, already-deployed thing beats the more complete one. So the claim held here is narrower than "Juice will win": the questions Juice answers will be asked, MCP by its own commitments will never answer them, and if the answers land in a protocol rather than a platform, that protocol must look like Juice. Whether it wins is a bet on direct machine-to-machine trade — a bet the market has not yet graded.
